## Conformance notes

_Requirement identifiers in these notes (for example `ST1`, `PAR3`, `DAT24`, `EVAL21`) are the NOTEBOOK_SPEC 1.1 numbering they were written against; NOTEBOOK_SPEC 2.0 renumbered its sections and the pull request that migrated this repository reports conformance against the 2.0 pre-flight checklist (§26) and report format (§30)._

- **Standalone carrier (ST1–ST6):** the primary path performs no clone, repository install, or repository import. Section 2 is `src/bart_summarization_pipeline/pipeline.py` verbatim (tagged `metadata.dimer.embedded_module`; the only rewrite makes the default weights directory working-directory-relative), Section 3 carries the model identity and the 8-file SHA-256 manifest inline and asserts they agree with the module before anything is fetched, and Section 1 carries the exact `pyproject.toml` runtime pins. `metadata.dimer.generated_from` records the repository, the revision generated from, the module's SHA-256, and the generator version.
- **Parity (PAR1–PAR4):** `tests/test_notebook_parity.py` and `tools/validate_release_assets.py` fail when the carried module, the inline manifest, or the inline pins differ from the repository, or when the notebook is not byte-identical to the generator's output.
- **Role stages:** `validate_inputs` (DAT24) writes `outputs/bart_summarization_input_manifest.json` — the document's identity and size, the exact generation settings that will be used (with their pinned source file), the schema and ceilings, the verdict, and one recorded rejection finding (`num_beams` above `MAX_NUM_BEAMS`); `evaluation_report` (EVAL21) writes `outputs/bart_summarization_evaluation_report.json`, whose verdict is always `not-measurable` because the repository ships no ROUGE or other metric helper; `needs` names the reference summaries, the caller's own ROUGE scorer and the faithfulness check a real evaluation requires (EVAL9), and `truncated` is recorded so cut-off outputs can be excluded.
- The notebook exercises `BARTSummarizationPipeline` carried verbatim in the notebook rather than reimplementing model loading or decoding; the pipeline pins the immutable upstream revision, stages the missing snapshot file through the package's `stage_missing_files(..., allow_download=True)`, loads only from a digest-verified local snapshot (`verify_snapshot`), and refuses remote model code. No cell outside the carried module calls `transformers`, `huggingface_hub` or `.generate(`.
- Decoding semantics (UNC1–UNC4): deterministic beam search (`do_sample=False`) returns the highest length-penalised beam; the pipeline emits no probability, confidence or quality score and applies no threshold; `truncated` is a length flag, not a quality signal; the caller owns any acceptance rule and must set it on reference summaries from their own domain. The generation defaults are the pinned `generation_config_for_summarization.json` (`max_length`/`min_length` converted to new-token counts), and the notebook says so.
- §20.7 does not apply (no fine-tuning); the notebook is inference-only and states the exclusions (no extractive guarantees, no chunking, no sampling, no fine-tuning). No intrinsic metric exists (EVAL9): the notebook says so, names what a real evaluation needs (references + ROUGE + faithfulness), quotes the upstream card's CNN/DailyMail ROUGE as upstream-reported, and presents the model card's smoke observation (81 tokens, largely extractive) as one measurement, not an expected value. Recorded `SHOULD` deviation: EVAL11 (no baseline — a lead-3 baseline would need references to compare against).
- Ceilings `MAX_TEXT_CHARS`, `MAX_INPUT_TOKENS` (reject, never truncate or chunk), `MAX_NEW_TOKENS`, `MAX_NUM_BEAMS`, `LENGTH_PENALTY_RANGE`, `MAX_NO_REPEAT_NGRAM_SIZE` and the `DEFAULT_*` generation values are surfaced before the model runs (DAT22/DAT23). The Colab form parameter is named `SUMMARY_MAX_NEW_TOKENS` so it cannot shadow the module's `MAX_NEW_TOKENS` ceiling.
- The default sample is synthetic text authored in code; `USE_BYOD` defaults to `False` so the sample path never opens an upload dialog.
- `tools/validate_release_assets.py` performs source validation only. It does not satisfy the
  clean-runtime execution requirement; a release review must confirm that a recorded clean run in
  `docs/release-verification.md` matches the notebook revision under review before the status is
  promoted to `Release-grade`.
